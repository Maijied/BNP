## MySQL schema (create migrations, run against cPanel MySQL)
- orders: id, created_at, name, shop_name, phone, district, address, model ENUM('A','B'),
  reg_number_bangla, reg_number_english, quantity, bracket BOOLEAN, plate_total,

- admins: id, email, password_hash (bcrypt), created_at

## LoraHost Payment Bridge (follow docs/PAYMENT_BRIDGE_API.md exactly)
1. POST https://lorahost.lorapok.tech/api/payment-bridge/v1/sessions
   Authorization: Bearer {LORA_BRIDGE_CLIENT_TOKEN}, JSON body: reference (order id),
   amount, return_url, customer. Sessions are created SERVER-SIDE ONLY.
2. Redirect customer to the returned checkout_url
3. Return: LoraHost redirects to return_url with reference, status, trx_id, amount,
   session_id, sig. Verify sig via HMAC over canonical sorted query params excluding
   sig, using LORA_RETURN_HMAC_TOKEN, before showing success.
4. Webhook: app/api/payment/webhook/route.ts verifies X-LoraHost-Signature over the
   RAW JSON body using LORA_WEBHOOK_HMAC_TOKEN; only then set payment_status='paid',
   store trx_id, and post an order summary to Discord.
5. Errors: handle 401, 403, 422 invalid_return_url, 429 rate_limited (backoff),
   503 bridge_disabled (show friendly message), and 409 duplicate PayStation invoice
   (create a NEW session, never reuse session_id).

## Notifications
- On verified webhook payment, POST order summary (order id, name, phone, model,
  reg number, total, trx_id) to process.env.DISCORD_WEBHOOK_URL. Server-side only;
  the webhook URL must never appear in client bundles.
